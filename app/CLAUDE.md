# CLAUDE.md — app/

SmartGreenhouse app (Ionic React 8 + React 19 + Capacitor 8). One build serves three places:
the Android APK, any browser on the greenhouse network, and the read-only `/kiosk` wall display
on the Pi. See `../README.md` for running the whole system and `../contract/README.md` for the
shared data contract.

## Data flow

```
ConnectionProvider   which backend: live (controller addresses tried in order, then cloud) or demo
  AuthProvider       live: POST /auth/login → access + refresh tokens + MQTT info; demo: local session
    GreenhouseProvider → LiveProvider (REST + MQTT over WebSocket, 5 s polling fallback, cached snapshot offline)
                       → DemoProvider (simulation/demoEngine.ts; every command acked SIMULATED)
      pages use useGreenhouse() only
```

- `src/contract/` — `types.ts` mirrors `contract/schemas` and the REST API; `registry.generated.ts`
  is generated by `contract/tools/gen_ts.py` (never edit by hand); `codes.ts` turns alert codes and
  refusal reasons into plain words.
- `src/api/client.ts` — REST client, 401 → refresh once → retry.
- `src/providers/types.ts` — the `GreenhouseData` contract both providers implement: raw `readings`
  per sensor, `zones` summaries, derived `metrics` (status vs. the active stage's thresholds),
  `actuators`, `openAlerts`, `sendCommand()`, `setActiveStage()`, and `data` (everything fetched on
  demand: history, thresholds, alerts, logs, reports, calibration, users).
- `src/providers/metrics.ts` — same aggregation as the controller: median of VALID readings per
  zone, mean of the zone medians. Failed reads are `null`, never 0.
- `src/simulation/demoEngine.ts` — in-app stand-in for the controller (same shapes, same audit
  action names). Tested in `demoEngine.test.ts`.

## Rules

- Commands only go through `sendCommand` → `POST /actuator/{id}/command`. The app never publishes
  to MQTT (its broker account is read-only). Show the ack with `components/useCommand.ts`.
- Water-moving commands ask for a duration and a confirmation; manual overrides expire on the
  controller (max 30 min), so never keep "manual" state in the app.
- Viewer accounts and the cloud path (while `remote_commands` is false) can't command:
  `useCommand().blocked` explains why; disable the control rather than hiding it.
- Anything capability-gated (energy, push) reads `meta.capabilities`, never a hard-coded flag.
- New device or sensor: add it to `contract/registry.yaml`, regenerate, and the pages pick it up
  from `meta.actuators` / `meta.sensors`.
- Styling: inline styles on `var(--sg-*)` tokens plus the `sg-*` classes in `theme/global.css`.
- Don't render `false`/`null` directly inside `IonRouterOutlet` (it crashes the outlet); route
  always, gate inside the page.

## Routes

`/login`, `/quick-setup`, `/kiosk` (no sign-in; `?demo=1`, `?token=`, `?api=`), and under `/tabs`:
dashboard, live-monitor, live-monitor/metric/:id, controls, fertigation, schedules (thresholds),
records, alerts, alert-detail/:id, calibration, settings, app-settings, profile, more, energy
(hidden unless `capabilities.energy`).

## Commands

`npm run dev` (Vite, expects the controller on :8000) · `npx tsc --noEmit` · `npm run test.unit` ·
`npm run build` · `npm run android:sync`
